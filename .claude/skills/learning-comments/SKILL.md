# learning-comments

このリポジトリのコードに、**学習用のコメント**を追加するスキルです。

目的は「後から自分が上から順に読んで、**なぜこう書いてあるのかまで**追えること」。レビュー用の指摘でも、API ドキュメントでもありません。

「何をしているか」だけのコメントは、コードの字面を日本語にしただけで理解に繋がりません。書くのは **理由と繋がり** です。

ただし **書きすぎない**。読むのに疲れるコメントは、無いのと同じくらい理解を妨げます。理由は 1 箇所につき 1 つに絞ります。

## 前提となる読者

**TypeScript / React を学習中の人**（＝このリポジトリのオーナー本人）を読者に置きます。サーバーサイド（Laravel / PHP）の実務経験はあるので、プログラミング一般の話は不要です。

説明する / しないの線引きはこうします。

| 説明する | 説明しない |
|----------|------------|
| 関数を引数に渡す構造（コールバック）と、それが「いつ・誰に」呼ばれるか | `if` / `for` / 変数宣言など、字面を読めば分かること |
| 関数の型注釈（`(x: T) => void` 等）が何を受け取り何を返す約束か | 一般的な HTTP・DB・データ構造の知識 |
| 戻り値の使い道が非自明なもの（関数を返す関数、購読解除用の関数など） | 三項演算子・分割代入など、MDN を引けば済む構文 |
| `as` による型アサーションが要る理由（外部由来で型が確定しない、等） | 命名から意図が明らかな処理 |
| ライブラリ固有オブジェクトの性質（例: `QuerySnapshot` は配列ではない） | Laravel 側で同種の概念を扱った経験がある一般論 |
| React 固有の挙動（副作用のクリーンアップ、依存配列、state 更新の反映タイミング） | |
| 非同期（`Promise` / `async` / `await`）でどこが待たれるか | |

迷ったら基準は 1 つ。「これは **このプロジェクト・このライブラリを知らないと引けない** か？」 YES なら書く、NO（MDN や公式ドキュメントで一発）なら書かない。

## 守ること

- **コードを変更しない。** 追加するのはコメントだけ。リネーム・整形・リファクタリング・処理の改善は、頼まれていない限り一切しない。改善案があるならコメントに埋めず、チャットで 1〜2 行の提案に留める
- **対象は指定されたファイル・行範囲だけ。** 「ついでに周辺も」をしない
- **import 群にはコメントを付けない**（既定）。何を import しているかは名前で分かるため。明示的に頼まれたときだけ付ける
- **書くのは「結果・意図」だけ。** 経緯・変更理由・参照元（「〇〇に合わせて」「以前は〜だった」「修正のため」）は書かない。詳細はグローバルの [`~/.claude/docs/code-comments.md`](~/.claude/docs/code-comments.md) に従う
- **字面の言い換えを書かない。** `// 変数を宣言`、`// ループを回す` のような、コードを読めば分かることの反復は入れない
- コメントは日本語。長い行は 2 行に折り返してよい

## 「なぜ」まで書く（頭の中に地図が残る粒度）

学習者が詰まるのは構文ではなく **「なぜこの形なのか」** です。非自明な箇所には、次の 4 つのうち当てはまるものを添えます。全部並べる必要はなく、その行で効くものだけを書きます。

| 書く内容 | 例 |
|----------|-----|
| **選ばなかった手との対比** | 「1 回取る（getDocs）なら戻り値で返せるが、何回も届くものは return では表せない。だからコールバックにする」 |
| **そうしないとどうなるか** | 「止めないと画面を離れたあとも監視が生き続け、消えた画面向けにデータが届き続ける」 |
| **どこと繋がるか（呼ぶ側・呼ばれる側）** | 「呼び出し側（React なら useEffect のクリーンアップ）で呼んでもらう」 |
| **ライブラリ / 外部仕様がそうなっている事実** | 「Firestore ではドキュメント ID が本文の外にあり、doc.data() には入っていない」 |

とくに次のような箇所は、理由を書かないと丸暗記で終わります。

- **戻り値・引数が関数**（コールバック、購読解除用の関数）: なぜ値ではなく関数をやり取りするのか
- **一見不要に見える一手**（条件なしなのに `query()` で包む、空配列を毎回作り直す）: それを省くと何が壊れるか
- **型に関する記述**（`as` によるアサーション、明示的な型注釈）: なぜ型が確定しないのか、実行時に何が保証されないのか
- **呼ばれるタイミングが自明でないもの**（初回にも呼ばれる、エラー後は再開しない）

一方で、理由が「言語仕様どおり」でしかないもの（`const` は再代入できない、など）には書きません。**このプロジェクト・このライブラリ・この設計を知らないと出てこない理由** だけが対象です。

## 短く書く（認知負荷を上げない）

理解の助けになるのは「腹落ちする理由が 1 つ」であって、網羅された背景ではありません。次を守ります。

- **1 箇所のコメントは 2〜3 行まで。** 効く理由が複数思いついても、**一番効くもの 1 つだけ**書いて次の行へ進む
- **理由の連鎖を辿らない。** 「なぜ → そのなぜ → さらにその背景」と掘らず、1 段目で止める
- **仕組みの内部を説明しない。** React の再描画の仕組み、Redux の内部構造、ライブラリの実装は書かない。**「そうしないとどうなるか」を 1 行**で言えば足りる
- **用語の定義を書かない。** 「state とは」「フックとは」の解説はコメントの仕事ではない。気になったときはチャットで聞く前提にする
- **既に書いた話を繰り返さない。** 同じファイル内で一度説明した概念は、2 回目以降は触れない
- 迷ったら削る。**入口だけ残して、深掘りはチャットに回す**

判断に迷ったときの基準は「これを読んだ人は、次にコードのどこを見ればいいか分かるか」。分かるなら十分で、それ以上は足しません。

## コメントの置き場所と粒度

上から読んだときに「意味のまとまりごとに 1 つ説明が出てくる」形にします。

1. **関数・定数の直前**: 何をするものかに加えて、**なぜこの作りなのか**を 1 つ。設計の分かれ目がある関数（同期 / 監視、値を返す / 関数を渡す 等）に限り、選択肢を 2 つ並べて「だからこちら」と繋げるために行数を足してよい
2. **引数の行の上**: 型注釈が非自明なとき（とくに関数型の引数）。「何を受け取り、何を返す関数か」「いつ・誰が呼ぶのか」「呼び出し側は何を預けることになるのか」まで書く
3. **処理ブロックの直前 / 行の隣**: なぜその一手が要るのか。積み先の配列を毎回作り直す理由、詰め替える理由、ID を別途取る理由など
4. **コールバックの引数位置**: 第 2 引数 / 第 3 引数がそれぞれ「データが届いたとき」「失敗したとき」など、呼ばれる条件が引数の位置で決まるものは、その位置に書く

行ごとに機械的に 1 コメントを付けて羅列にしない。まとまりが短ければ 1 つにまとめます。

長さの目安は、**理由を 1 つ書いたら次の行へ進む** くらい。1 箇所で背景を語り尽くそうとせず、関係する話はそれが出てくる行に置いて、読み進めながら繋がるようにします。

## 進め方

1. 対象ファイルを **指定された行範囲だけ** Read する
2. 参照している型・設定ファイル（`src/type/*.ts`、`src/firebase/firebaseconfig.ts` 等）を必要な分だけ読み、コメントに書く内容の裏を取る。推測で「たぶんこう」と書かない
   - **「なぜ」は裏が取れたものだけ書く。** ライブラリの挙動（いつ呼ばれる / エラー後どうなる / 何を返す）が曖昧なら、context7 で公式ドキュメントを引いて確認する。確認できなければ、そこは書かずに動作の説明だけに留める（間違った理由は、理由が無いより悪い）
3. Edit でコメントを差し込む（コードの文字列は 1 文字も変えない）
4. チャットでは、どのファイルの何行目に何を足したかを数行で報告する。ファイル全文やコメント文面をチャットに再掲しない

## 例

既定の長さはこれくらい（`src/components/ChatContainer/ChatList.tsx`）。1 箇所につき理由 1 つで、すぐ次の行へ進みます。

```ts
    // 画面に出すチャンネル一覧。ただの変数ではなく state にするのは、
    // setChannelRefs で更新したとき React が画面を描き直してくれるのがこの形だけのため
    const [channelRefs, setChannelRefs] = useState<ChannelRef[]>([]);

    // 通信の開始のような「描画そのものではない処理」は useEffect の中でやる
    useEffect(() => {
        // 渡した関数はデータが届くたび呼ばれる。そのつど state を入れ替えて画面を更新する
        const unsubscribe = subscribeChannels((channelRefs) => {
            setChannelRefs(channelRefs);
        });
        // useEffect が返した関数は、この画面が消えるとき React が呼ぶ。
        // ここで監視を止めないと、もう無い画面に向けてデータが届き続ける
        return () => unsubscribe();
        // 第 2 引数の空配列は「最初の 1 回だけ実行する」の意味。
        // 付け忘れると描画のたびに監視が増えていく
    }, []);
```

行数を足してよいのは、設計の分かれ目があるときだけ（`src/features/channel/channelAPI.ts` の抜粋）。

```ts
// channels コレクションを「監視」する関数。
//
// Firestore からのデータ取得には 2 通りある。
//   1 回だけ取る（getDocs）  … 結果が 1 回で確定するので、戻り値で返せる
//   変化を監視する（onSnapshot）… 他人がチャンネルを追加するたび結果が届く。何回届くか事前に分からない
// チャットは他人の追加を即座に画面へ出したいので後者を使う。
// ただし「何回も届くもの」は return では表現できない（return は 1 回きり）。
// そこで結果の渡し方をひっくり返し、呼び出し側から渡された関数を届くたびに呼ぶ形にする
export const subscribeChannels = (
    // 「ChannelRef の配列を受け取り、何も返さない関数」という型。
    // この関数自身がここで実行されるのではなく、あとで（データが届いたとき）呼ばれる。
    // 呼び出し側は「データが届いたらこれをやってくれ」という処理を関数の形で預けることになる
    onChannelsUpdated: (channels: ChannelRef[]) => void
) => {
    // onSnapshot は監視を始めると同時に「その監視をやめる関数」を返してくる。
    // 監視は放っておくと画面を離れたあとも生き続け、
    // 消えたはずの画面向けにデータが届き続ける（通信もリスナーも残る）。
    // それを止められるのは監視を始めた本人だけなので、止めるための関数をそのまま呼び出し側へ返し、
    // 呼び出し側（React なら useEffect のクリーンアップ）で呼んでもらう
    return onSnapshot(
        q,
        ...
                    // doc.data() は「何のフィールドが入っているか分からない」型で返ってくる。
                    // Firestore 側に型の情報が無く TypeScript も中身を知れないため、
                    // as で「これは Channel として扱う」と宣言している。
                    // 実行時に中身が検査されるわけではないので、保存されている形とこの型がずれると実行時に壊れる
                    channel: doc.data() as Channel,
```

比較のため、同じ箇所を「何をしているか」だけで書くとこうなります。**これは不十分な例** です。

```ts
// NG（動作の言い換えで止まっている。なぜ関数を返すのか、返さないと何が起きるのかが無い）
// onSnapshot の戻り値は監視をやめる関数。それをそのまま return する
```

説明の軸は「コールバックがいつ・誰に呼ばれるか」「なぜ値ではなく関数をやり取りするのか」「型アサーションで何が保証されないのか」の 3 つです。

## 使い分け

- **このスキル**: コードそのものにコメントを残して、後からファイルを開いたときに読めるようにする
- `impl-codewalk`（グローバル）: 実装一式を画面 + Obsidian ノートで理解する。コードには手を入れない
- `diff-review`（グローバル）: 変更をレビュー・承認するための指摘を出す
